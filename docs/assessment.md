# Atoms Demo 笔试说明

## 我做了什么

打开 Demo，输入一个想做的小应用。左边是项目对话，能看到构建计划和进度。右边是生成的网页，可以直接点按钮、填表单。想再加一个功能就在左边接着说，构建成功后会多一张版本卡。也可以先打开旧版看看，再决定要不要恢复。

## 为什么这样做

我先做了两轮构建，因为第二轮更能看出产品能不能用。比如温度换算器已经能从摄氏度算华氏度，再加反向换算时，前一个功能也得继续能用。后端会把当前版本的源码和这次修改要求一起发给模型。新版本启动失败时，工作台会保留上一版，用户还能继续用它。

构建由一个 Agent 编排。同一个模型先把需求拆成几步，再输出 HTML、CSS 和 JavaScript。服务端检查返回格式和 JavaScript 语法，代码在浏览器的沙箱里运行。格式或语法有问题时会尝试修一次。首版只生成无需后端的单页应用，这样评审打开预览就能操作，生成物也不用单独启动服务。

项目、对话和源码版本都保存在当前浏览器里，刷新后可以从「最近项目」打开。沙箱里临时输入的数据会随预览重载重置，也没有跨设备同步。

开发时用 Codex 拆分任务、写代码和跑浏览器测试。Demo 的模型请求走 Atoms API。

## 做到哪了

- 用固定的测试响应在浏览器里跑过两轮。v1 输入 25°C，点击换算后得到 77°F。v2 加了反向换算，两个方向分别测到了 77°F 和 25°C。
- 还测了三种情况。候选版本启动报错时保留 v2，查看 v1 时仍以 v2 为当前版本，恢复 v1 后生成 v3。刷新重开项目能看到 v3 和之前的对话。
- 真实模型联调用的是另一个需求，生成一个有 12 个名额的手冲工作坊预约台。Atoms 接口在拆解需求时返回额度不足，还没有拿到真实生成的版本。线上 Demo 和公开仓库也还没发布。

## 接下来先做什么

1. 先用有额度的 API Key 跑完两轮真实生成。首轮测试预约和删除时的名额变化，第二轮加姓名筛选，再测一遍原来的新增和删除。
2. 通过后再发布 Demo 和 GitHub 仓库。给匿名生成接口设请求上限，用无痕窗口从输入需求开始走一遍。
3. 如果还有时间，把这两轮的交互检查做成可以重跑的浏览器测试。版本一多，手动点一遍很容易漏掉原本能用的功能。
