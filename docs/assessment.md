# Atoms Demo 开发说明

## 参考了 Atoms 的什么

这次做的是一个能用对话创建和修改应用的工作台。我参考了 Atoms 的项目对话、构建过程和预览。用户可以输入自己的需求，在左侧看构建计划和进度，在右侧直接操作生成的网页。再发一句修改要求，成功后会在同一个项目里多一个版本。[在线 Demo](https://atoms-demo.1443343615.workers.dev/)

## 内容生成怎么实现

生成只有一个 Agent，入口是后端的 `generateApp`。它用 Cloudflare Workers AI 的同一个 Qwen 模型完成规划和写代码。

1. **先列计划。** 接口收到需求后，第一次调用模型，让它返回两到四条构建步骤。例如做计算器，可以分成设计输入表单和实现计算逻辑。接口把计划和各阶段的进度发给前端。
2. **再生成代码。** 第二次调用把原需求、计划和已有源码交给模型。模型返回标题、变更摘要、React 挂载节点、CSS 和组件代码。需要在服务端执行业务规则时，模型还会生成一个 JavaScript 后端模块。修改应用时，Agent 会读当前版本的前后端源码。
3. **检查输出。** 服务端检查字段是否齐全、有没有超长，并用 Acorn 解析 JavaScript。这里检查的是格式和语法。发现问题时，把出错原因和原输出交给模型修一次。[Agent 源码](../lib/generator.js)
4. **跑起来再切版本。** 前端先把代码放进一个沙箱 iframe 试启动。收到就绪消息后开始交互验收，随后保存并打开新版本。启动报错或超时会显示失败信息，当前版本仍能用。[工作台](../app/page.js) · [预览代码](../lib/preview.js)

我在版本卡里加了交互验收。模型写代码时也会给出几条检查步骤。浏览器在独立的 iframe 里执行填写、点击和断言，每条都从空白应用开始。修改时会原样重跑上一版最多四条检查，并跑本轮的新检查。失败时卡片会显示哪一步出错、预期是什么、页面上实际读到了什么。有失败项的版本仍可打开，也可以从历史里恢复旧版。

项目、对话和源码版本保存在当前浏览器里，刷新会回到当前项目。业务记录由后端保存，筛选词这类临时状态随预览重载重置。已有的 `AtomsData` 应用仍使用原来的数据接口。

## 用了什么沙箱

React 预览运行在浏览器的 sandbox iframe 里。它通过 `AtomsBackend.call` 把操作交给工作台，由主 Worker 按项目和版本查找后端源码，再通过 [Worker Loader 配置](../wrangler.jsonc) 加载到 **Cloudflare Dynamic Workers**。部署这项能力需要 Workers Paid。预约台用一个 JavaScript 模块就能处理新增、删除和容量校验，所以选了 Dynamic Workers。

生成的模块只拿到本次操作、参数和当前记录。沙箱关闭出网，主 Worker 负责把成功的修改写入项目自己的 SQLite Durable Object。两笔预约并发时，如果它们读到了同一份记录，后提交的请求会用最新记录重跑规则。验收用另一个 Worker 实例执行同版代码，每项检查从临时记录开始。[后端执行入口](../lib/project-backend.js) · [项目存储](../lib/project-data-store.js)

## 部署和验收

我在本机登录 Wrangler，用 `npm run build:cloudflare` 构建，再跑 `npx wrangler deploy` 上传 Worker 和静态资源。部署完成后，验收单独对公网地址跑。[部署配置](../wrangler.jsonc)

我先用 Codex 给生成接口喂固定响应，检查浏览器里的版本切换、刷新恢复和启动失败后保留旧版。上线后，再用 Codex 编写的 Playwright 脚本开一个干净的浏览器会话，走一遍真实模型：

1. 输入自定义需求，让 Agent 做一个每小时 75 元的排练室费用计算器。等 v1 出来后，在预览里填两小时，点计算，检查结果是 150 元。
2. 在对话里发「加一个会员八折选项」。等 v2 出来后，勾选会员再计算，检查折后价是 120 元，取消勾选后还是 150 元。
3. 刷新，从「最近项目」重新打开，检查修改指令和 v2 都还在。

第一次线上验收时，点计算没有结果。Codex 取出生成的源码，确认表单绑了提交事件，问题出在 iframe 把事件拦住了。改完后用同一份源码复测，表单能触发计算，浏览器也仍会拦住实际的表单提交。最终用 `npm run test:e2e` 从空白会话重跑，三步都通过了。[Playwright 验收脚本](../tests/e2e/generation.spec.mjs)

我又用 Playwright 测了一个 12 人的手冲工作坊预约台。v1 给林青预约 3 人，再给周野预约 2 人，剩余名额从 12 变为 9，再变为 7。删除周野后恢复到 9，林青的记录还在。

接着发一句话加姓名筛选。第一次修改超时，页面保留了 v1，我点「重试」生成了 v2。在 v2 重新新增两笔后，筛选「林」只显示林青，剩余名额还是 7。删掉林青后恢复到 10，清空筛选能看到周野的记录。

上线后又跑了一遍计算器。v1 的两条检查都通过了。加上会员八折后，v2 的四条检查也都通过，包括原来的费用计算、空值提示、新增的折扣价和原价。

我还用固定响应测了失败的情况。计数器从每次加一改为加二后，旧检查的第三步预期是 2，浏览器实际读到 4。新检查通过，用户预览里的计数仍从 0 开始。


## 后端沙箱验收

我用 Codex 固定模型返回的预约台源码，在本机 Wrangler 的真实 Worker Loader 上跑 Playwright。先预约 3 人，剩余名额从 12 降到 9。再直接向 API 提交 10 人预约，服务端返回 `422`，刷新后还是一笔预约、剩余 9 人。另用两笔并发的 8 人预约验证，只接受了一笔。第二版加了单笔最多 4 人的规则，服务端拒绝了 5 人预约，第一版的记录仍在。

Cloudflare 已部署带 Worker Loader 的版本，旧版任务的线上持久化回归也通过了。线上用真实模型生成预约台时，分别遇到推理失败、超时和计划格式错误，均停在生成阶段。完整的「真实模型生成 → 线上沙箱执行」还没验完。用 `npm run test:e2e -- --grep 预约后端` 可以重跑。[验收脚本](../tests/e2e/generation.spec.mjs)
